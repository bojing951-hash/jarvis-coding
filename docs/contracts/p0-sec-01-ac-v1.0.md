# 二、审计原则

本轮是安全与执行正确性验收。

不是功能展示验收，也不是文档完整性验收。

Agent 2 必须坚持：

1. 独立读取实际源码。
2. 核验目标 Commit。
3. 检查每条危险调用链。
4. 执行正向与负向测试。
5. 不以开发者报告代替证据。
6. 不以 Mock 结果冒充真实调用。
7. 不以模型答复证明权限控制。
8. 不以测试数量证明质量。
9. 不擅自修改验收契约。
10. 不在没有证据时推定 PASS。

开发人员提交的测试结果可以作为待核验证据，但不能自动成为审计结论。

# 三、阻断性验收条件

以下条件均为本轮必须核验的要求。

## AC-01｜固定版本与开发范围

**前置条件**

存在指定开发基线及本轮目标 Commit。

**执行动作**

检查 Git 提交关系、开发分支、Diff 和文件清单。

**预期结果**

- 修改建立在固定基线之上。
- 未擅自改变原始开发基线。
- 未直接修改 main。
- 未引入无关架构重构。
- 所有实际修改均可追溯。

**核验证据**

Git Commit SHA、父提交关系、Diff、变更文件清单及分支状态。

---

## AC-02｜MCP 不得提供未经授权的 Shell 能力

**前置条件**

JARVIS 主 Agent 不具有通用 Shell 权限。

MCP 可以正常创建任务。

**执行动作**

通过 MCP 提交含有 Shell 操作要求的任务配置。

包括尝试利用：

- verify
- executor_config
- Workflow Spec
- 其他可控字段

**预期结果**

未经可信授权的 Shell 操作被拒绝。

不能通过创建普通任务间接执行任意 Shell 命令。

**核验证据**

MCP 调用记录、拒绝结果、执行器日志和测试标记文件未被创建的证据。

---

## AC-03｜命令注入防护

**前置条件**

系统存在允许执行的固定验证命令。

**执行动作**

尝试通过命令参数加入额外 Shell 操作。

包括命令分隔符、变量替换和其他解释器语法。

**预期结果**

不可信参数不能改变实际执行程序及命令范围。

系统不得将 Agent 提供的任意字符串直接交给 Shell 解释执行。

**核验证据**

实际子进程 argv、测试日志、注入结果与外部副作用检查。

---

## AC-04｜可信验证配置

**前置条件**

已通过可信控制入口登记允许执行的验证配置。

**执行动作**

分别执行：

A. 引用合法验证配置。

B. 引用不存在的验证配置。

C. 试图覆盖合法配置的命令内容。

**预期结果**

A 可以在授权条件满足时执行。

B 必须拒绝。

C 必须拒绝或忽略不可信覆盖参数，且不能产生额外执行。

**核验证据**

可信配置内容、调用记录、实际执行程序和退出码。

---

## AC-05｜真实人工审批

**前置条件**

存在需要审批的高风险任务。

**执行动作**

分别测试：

A. 用户未批准。

B. 模型输入 `approved=true`。

C. 模型声称“用户已经批准”。

D. 普通 MCP 调用 `task_approve`。

E. 通过独立可信授权入口完成真实批准。

**预期结果**

A、B、C、D 不得使任务获得高风险执行权限。

E 在授权来源和授权范围均有效时可以通过。

若使用本地审批入口，必须证明普通 Agent 和执行器不能通过自身可用能力伪造该审批。

若使用飞书审批，必须证明授权身份来自可信事件或平台认证信息，而不是模型转述。

**核验证据**

审批来源、身份验证机制、权限检查日志、审批记录及实际执行结果。

---

## AC-06｜审批内容绑定

**前置条件**

任务 A 已获得合法审批。

**执行动作**

审批后分别修改：

- 执行器
- 执行模式
- 工作目录
- 允许修改的文件范围
- 验证配置
- Commit 权限
- 其他影响执行权限的关键参数

**预期结果**

任何影响授权范围的变更均不能继续使用原审批执行。

系统必须重新审批或拒绝。

**核验证据**

审批前后任务摘要、授权记录、拒绝日志及实际执行结果。

---

## AC-07｜审批过期与重复使用

**前置条件**

存在合法的限时或一次性授权。

**执行动作**

测试：

- 过期授权。
- 重复使用授权。
- 使用授权执行不同任务。
- 使用授权执行不同项目操作。
- 使用旧版数据库审批字段。

**预期结果**

授权不得被扩大、复用到无关操作或通过历史字段恢复。

不满足当前审批要求时必须拒绝。

**核验证据**

授权 ID、授权范围摘要、状态变化、执行记录和拒绝事件。

---

## AC-08｜全部执行入口共用权限门禁

**前置条件**

同一种高风险操作可以由不同入口发起。

**执行动作**

分别通过：

- MCP
- CLI
- 普通 Task
- Workflow
- 可用的其他执行入口

发起未经授权的操作。

**预期结果**

所有入口均受到相同的核心权限规则约束。

不得出现一个入口拒绝，另一个入口直接允许的情况。

可信管理员入口可以拥有明确不同的权限，但必须独立验证其授权来源，不能由普通 Agent 伪造。

**核验证据**

调用链检查、接口测试、执行结果和安全策略判定记录。

---

## AC-09｜项目执行目录限制

**前置条件**

存在两个独立项目 A、B。

项目 A 仅被授权操作自己的工作目录或明确登记的仓库。

**执行动作**

项目 A 的任务尝试访问：

- 项目 B 工作目录。
- 未授权 Git 仓库。
- 任意外部目录。

**预期结果**

未经授权的目标被拒绝。

不能通过任务配置扩大项目资源范围。

**核验证据**

目录权限配置、调用记录、目标文件状态和拒绝原因。

---

## AC-10｜路径穿越与符号链接保护

**前置条件**

系统存在合法执行目录。

**执行动作**

尝试使用：

- `../`
- 绝对路径
- 符号链接
- 指向其他项目的链接
- 指向未授权目录的链接

绕过执行范围。

**预期结果**

路径规范化和实际访问边界能够阻止越权。

不能仅依赖字符串前缀判断路径归属。

**核验证据**

测试路径、真实路径解析结果、拒绝日志及越权目标未变化的证据。

---

## AC-11｜外部执行器真实权限限制

**前置条件**

Claude Code 执行器可以运行受控任务。

**执行动作**

在测试环境中尝试：

- 未授权写入。
- 使用未授权工具。
- 访问工作范围之外的测试文件。
- 读取不应暴露的测试环境变量。

**预期结果**

执行器不能通过自行选择工具、路径或继承环境变量扩大权限。

如果运行环境无法提供可靠的写入隔离，写模式必须保持 Fail Closed，不能被标记为已安全实现。

**核验证据**

实际进程配置、沙箱或权限配置、工具调用记录、目标文件状态及环境变量隔离测试。

---

## AC-12｜合法写入的正向验证

**前置条件**

存在一次性测试 Git 仓库。

仓库包含一个可复现的软件缺陷。

用户通过可信方式批准相应写入操作。

执行范围和校验配置均已固定。

**执行动作**

调用 Claude Code 修改测试仓库代码。

执行规定测试。

**预期结果**

- 模型在授权范围内完成修改。
- 不修改无关目录。
- 真实测试执行成功。
- 实际代码 Diff 可核验。
- 执行状态和证据一致。

如果本轮实现选择暂时锁定所有写模式而无法完成该场景，则本项不能判定 PASS；应标记未满足，并不得声称已恢复安全可用的写入闭环。

**核验证据**

真实执行日志、文件 Diff、测试输出、授权记录和最终状态。

---

## AC-13｜测试失败阻止 Commit

**前置条件**

Claude Code 已完成修改，执行器自身返回成功。

但规定测试失败。

**执行动作**

触发自动提交流程。

**预期结果**

- 不执行 Git Commit。
- 不生成新的提交。
- 任务不得标记为成功完成。
- 记录真实测试失败原因。
- 不能通过模型生成的“测试已通过”文字绕过。

**核验证据**

测试退出码、Git HEAD 前后值、执行日志、任务状态。

这是阻断性条件。

---

## AC-14｜缺少有效测试不得自动提交

**前置条件**

任务要求自动提交代码。

但未配置可信校验，或校验未实际执行。

**执行动作**

尝试提交。

**预期结果**

提交被拒绝。

不能将空校验、伪造结果或模型文本视为真实通过。

**核验证据**

提交前检查结果、Git HEAD、任务状态及拒绝日志。

---

## AC-15｜Git 提交范围控制

**前置条件**

测试仓库存在与本次任务无关的修改。

**执行动作**

执行一个经过授权的代码修改和提交任务。

**预期结果**

未经授权的文件不能进入提交。

系统应当拒绝不干净的初始工作树，或通过有证据的隔离机制保证提交范围准确。

不得无条件使用 `git add -A` 将所有文件加入提交。

**核验证据**

初始 Git Status、任务 Diff、实际 Commit 文件列表及最终工作树状态。

---

## AC-16｜成功提交的真实证据

**前置条件**

任务合法授权。

执行器完成修改。

规定测试通过。

提交范围合法。

**执行动作**

执行 Git Commit。

**预期结果**

- Git Commit 真正成功。
- 返回真实完整 SHA。
- Commit 包含预期修改。
- 测试结果与被提交版本一致。
- Commit 失败不得报告任务成功。

**核验证据**

Git Log、Commit SHA、提交 Diff、校验输出与 Execution 记录。

---

## AC-17｜取消后不得继续产生副作用

**前置条件**

执行器任务正在运行。

**执行动作**

分别在以下阶段取消：

- 执行过程中。
- 验证开始前。
- 提交开始前。

**预期结果**

取消成功后不得启动新的执行、验证或提交操作。

已取消状态不得被后续成功回写覆盖。

**核验证据**

进程状态、取消时间、任务状态、执行记录及 Git HEAD。

---

## AC-18｜取消失败不得虚报成功

**前置条件**

存在无法成功终止的进程，或模拟终止失败。

**执行动作**

请求取消。

**预期结果**

系统不得直接报告取消成功。

必须报告实际终止结果、错误或无法确认的状态。

不得将未确认终止的进程记录为已经安全停止。

**核验证据**

进程信号结果、状态转换、错误日志和任务记录。

---

## AC-19｜并发与重复执行保护

**前置条件**

同一任务处于可执行状态。

**执行动作**

并发发起两次执行请求。

**预期结果**

不得启动两次高风险执行。

不得消耗同一授权生成两次独立副作用。

不得产生重复 Git Commit。

**核验证据**

Execution 数量、进程数量、授权使用记录及 Git 历史。

---

## AC-20｜暂停、失败与重启保护

**前置条件**

存在已暂停项目、已失败任务和异常退出后恢复的任务。

**执行动作**

分别尝试：

- 在暂停项目内启动新的执行。
- 继续已经失败的高风险任务。
- 使用过期审批重试。
- 重启后自动继续未确认的提交操作。

**预期结果**

所有操作必须遵守真实任务状态与授权有效性。

不得通过重启、重试或 Workflow 恢复绕过原安全门禁。

**核验证据**

SQLite 状态、事件记录、执行数量、Git 历史及拒绝日志。

---

## AC-21｜执行证据完整性

**前置条件**

完成一次合法执行和至少一次被拒绝执行。

**执行动作**

检查 SQLite、日志及交付证据。

**预期结果**

关键操作可以追溯：

- 谁或哪个可信来源授权。
- 授权什么操作。
- 实际执行了什么。
- 使用哪个执行器。
- 操作了哪个项目。
- 实际执行结果是什么。
- 是否通过测试。
- 是否发生 Commit。
- 为什么拒绝或失败。

敏感密钥不得进入 Git 或公开日志。

**核验证据**

Execution、Task、审批记录、事件日志及脱敏后的审计证据。

**预期结果**

如果真实外部模型或飞书不可用，应区分环境 WAITING 和已确认代码回归。

**核验证据**

原有及新增测试结果、必要的真实调用记录和失败分析。

# 四、必须执行的端到端场景

以下场景用于验证跨模块安全性质。

## E2E-01｜未授权 Shell 拒绝

创建一个未授权任务，通过 MCP 填写危险验证命令。

预期：

任务不能执行该命令，测试标记文件不存在。

## E2E-02｜伪造审批拒绝

使用 `approved=true`、模型声称用户同意、普通 MCP 审批调用等方式尝试运行写任务。

预期：

任务被拒绝，代码未被修改。

## E2E-03｜真实审批后合法执行

经可信审批，在独立测试仓库执行合法代码修改。

预期：

完成修改、测试和合法提交。

全部结果有真实证据。

## E2E-04｜测试失败阻断提交

在测试故意失败的情况下触发自动提交。

预期：

Git HEAD 不变，任务不能标记成功。

## E2E-05｜无关文件不能进入 Commit

在工作树放置与任务无关的修改。

预期：

该修改不进入任务 Commit。

若系统选择拒绝不干净工作树，也视为符合本场景。

## E2E-06｜跨项目和路径逃逸

让项目 A 的执行器访问项目 B 或授权目录之外的文件。

同时测试符号链接绕过。

预期：

操作被拒绝，目标文件未变化。

## E2E-07｜取消竞态

启动长时间执行任务。

在验证或提交前取消。

预期：

取消后的新副作用不发生。

无法真正终止时必须明确报告。

## E2E-08｜Workflow 权限绕过

通过 Workflow Spec 创建包含高风险配置的执行节点。

预期：

其权限检查与直接创建任务一致，不存在额外绕过入口。

## E2E-09｜审批绑定与重放

批准任务后修改关键参数。

再尝试使用同一批准执行或重复执行。

预期：

原授权失效或拒绝重复使用。

## E2E-10｜正常非编程工作流回归

创建一个正常的非编程多 Agent 工作流。

预期：

它能够在无需高风险执行权限的情况下正常运行。

证明安全修复没有把整个 JARVIS 调度功能禁用。

Agent 3 必须提供实际证据。

Agent 2 应独立检查，而不是只接受测试摘要。

至少包括：

| 证据编号 | 必须提供的证据 |
|---|---|
| EV-01 | 固定开发基线与目标 Commit |
| EV-02 | 完整代码 Diff |
| EV-03 | 修改文件清单 |
| EV-04 | 安全执行调用链说明 |
| EV-05 | 审批机制与可信来源说明 |
| EV-06 | Shell 注入负向测试 |
| EV-07 | 未授权写入负向测试 |
| EV-08 | 跨项目和路径逃逸测试 |
| EV-09 | 测试失败阻断 Commit 的真实证据 |
| EV-10 | 合法执行、验证、Commit 的完整证据 |
| EV-11 | Git 提交范围测试 |
| EV-12 | 取消与并发竞态测试 |
| EV-13 | 原有功能回归测试 |

# 六、验收裁决规则

## 1. 单项状态

每条 AC 使用以下状态：

**PASS**

已获得充分证据，实际结果满足要求。

**FAIL**

通过源码、实际执行或其他有效证据确认违反要求。

**WAITING**

缺少必要环境、凭据或执行证据，尚不能判断是否满足要求。

**NOT APPLICABLE**

仅在契约明确允许的条件下使用，必须解释适用边界；不能以此排除本轮必须验证的安全性质。

## 2. 阻断规则

AC-01 至 AC-22 均为本轮必须处理的验收条件。

任何一条阻断性条件 FAIL：

**最终结论 FAIL。**

如果存在尚未完成的必需验证，但没有确认缺陷：

**最终结论 OPEN / WAITING，不得判定 PASS。**

只有全部必需条件满足、端到端安全场景获得相应证据，且没有未解决的阻断性缺陷，才能判定：

**PASS。**

文档声明、模拟测试或开发者自行评价不能替代必要的真实执行证据。

## 3. 安全降级

如果某项危险操作在当前环境下无法安全实现，可以暂时禁用。

禁用必须真实有效，且不能经其他入口绕过。

但禁用不自动等同于原功能已经完成。

如果合法写入闭环因此无法完成 AC-12、AC-16 等要求，本轮不能获得完整 PASS。

必须区分：

“危险功能已安全关闭”

与

“危险功能已经安全可用”。

## 4. 审计结果与发布状态

Agent 2 的 PASS 表示该固定目标 Commit 满足本契约。

不表示：

- 整个 JARVIS 产品已经完成。
- 蓝图全部 MVP 条件已经满足。
- 可以自动发布 main。
- 可以自动开启高风险权限。

是否发布和合并由用户决定。
