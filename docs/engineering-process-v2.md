# JARVIS 工程开发与验收流程 v2.0

> 版本：2.0  
> 生效范围：JARVIS 的修复、门禁、基础设施与验收活动  
> 与冻结契约的关系：本文件只规定“如何开发、如何证明、如何移交”，**不修改任何已冻结验收契约**。若本文件与冻结契约冲突，以冻结契约为准。

## 1. 目的

本流程把“开发完成”与“可验收”分开，确保：

1. 开发开始前，固定版本、契约、范围、输入、技术前置条件和环境均已核实。
2. 高风险或依赖操作系统的方案先做最小可行性实验，不以未经验证的设计直接扩展为完整功能。
3. 确定性缺陷先有失败复现，再有修复；旧版本必须失败，新版本必须通过同一测试。
4. 交付必须经过自动化质量门禁和真实环境证据检查，CI 失败不得宣布可验收。
5. 最终 PASS 只能由独立验收方给出，开发方不得自证通过。

## 2. 角色与职责

| 角色 | 职责 | 不得做的事 |
|---|---|---|
| 用户 / 项目所有者 | 确定范围与优先级；提供必要环境、账号、授权或风险接受决定 | 不得被开发方以“已完成”替代真实决策 |
| Agent 3（开发方） | 执行 G0–G2；提交代码、测试、证据与缺陷记录；移交 G3 | 不得自行宣布最终 PASS；不得用自述替代独立证据 |
| Agent 2（独立验收方） | 在固定 Commit 上独立检查代码、契约、测试、CI 与真实环境证据；给出 PASS / FAIL / WAITING | 不得在缺少环境时用开发方叙述补足证据 |
| CI / 自动化 | 在固定 Commit 上执行必需检查并留下可追溯结果 | 不得被本地运行结果替代 |

## 3. 状态定义

| 状态 | 含义 |
|---|---|
| `BLOCKED` | 缺少必要条件（版本、契约、输入、环境、权限、依赖等），不得开始或继续该门禁 |
| `BLOCKED_FEASIBILITY` | 技术可行性实验证明当前所有合规路径不可用 |
| `WAITING_USER` | 需要用户亲自完成的操作（Touch ID、系统密码、账号登录、授权决定等） |
| `READY_TO_DEVELOP` | G0 全部通过 |
| `DEVELOPMENT_IN_PROGRESS` | G1 进行中 |
| `READY_FOR_INDEPENDENT_AUDIT` | G0–G2 全部通过，可以移交 G3 |
| `WAITING` | 独立验收方缺少必要环境或证据，暂不能给出结论 |
| `PASS` / `FAIL` | 只能由独立验收方或用户给出 |

**总原则：任一门禁未满足，不得宣布整个工程任务 `READY`。**

## 4. G0｜开发准备门禁

开发前必须逐项核实并留存证据；任一必需项缺失即标记 `BLOCKED`，不得宣称 `READY`。

### 4.1 必查项

| 编号 | 检查项 | 最低证据 |
|---|---|---|
| G0-01 | Git 固定版本 | `git rev-parse HEAD`；固定 Commit 与目标一致 |
| G0-02 | 正式验收契约 | 契约文件路径、字节数、SHA-256；与冻结值一致 |
| G0-03 | 开发范围 | 工作包编号、允许修改的文件/目录、明确不做的内容 |
| G0-04 | 必要输入文件 | 代码、配置、文档、测试、镜像/依赖清单等实际存在且可读 |
| G0-05 | 技术前置条件 | 所需 OS、CPU 架构、运行时、签名身份、Docker、网络、账号等 |
| G0-06 | 当前环境支持 | 在目标环境实际探测，而不是假设；记录失败项 |
| G0-07 | 分支隔离 | 从固定 Commit 创建独立分支；`main` 未被修改 |
| G0-08 | 基线状态 | 修复前测试、CI 或已知失败的原始结果 |

### 4.2 退出条件

- 全部必需项通过：记录 `READY_TO_DEVELOP`。
- 任一必需项缺失：记录 `BLOCKED`，写清缺失项、影响、责任方和解除条件。
- **不得**在条件不满足时以“先做起来再说”为由宣称 `READY`。

## 5. G1｜技术与实现门禁

### 5.1 高风险 / 未知 / 依赖操作系统的方案

必须先完成最小可行性实验，再决定是否扩展为完整实现。

实验要求：

1. 在隔离的临时环境中进行，不使用真实生产授权、真实用户密码或生物识别数据作为测试数据。
2. 明确假设、实验步骤、成功/失败判据和可复现命令。
3. 优先参考厂商官方文档；区分“错误码推测”与“实际日志/实验证明”。
4. 记录实际构建产物，而不只看源码或配置文件。
5. 若技术不可行，返回 `BLOCKED_FEASIBILITY`，不得把未经验证的设计直接扩展为完整功能。
6. 需要真实 Touch ID 或系统密码时，通知用户亲自完成；不得记录密码或生物识别信息。

### 5.2 确定性代码缺陷

必须先建立失败复现，再实施最小修复。

必须证明：

1. **旧版本存在问题**：在修复前的固定版本上，同一测试失败。
2. **新版本通过同一测试**：修复后，同一测试通过，且断言没有被放宽或删除。
3. 如缺陷属于实际产品代码，而非测试环境或配置问题，必须提交缺陷记录：编号、影响、根因、修复、证据。
4. 不得为了 CI 通过而进行与缺陷无关的功能重构。

### 5.3 安全边界

- 不得以“先通过 CI”为由降低身份认证、隔离、审批或审计标准。
- 需要改变安全保证时，必须由用户明确接受，并记录风险；开发方不得自行决定。

## 6. G2｜自动质量门禁

开发完成必须经过以下检查，缺一不可：

| 检查 | 要求 |
|---|---|
| 单元测试 | 全部必需用例通过 |
| 失败注入测试 | 取消、超时、拒绝、篡改、失联等路径有可复现证据 |
| 必要集成测试 | 真实链路或受控替身链路通过；替身不得冒充真实环境 |
| GitHub CI | 在固定目标 Commit 上实际运行；必需检查全部通过 |
| 真实环境专项验证 | CI 无法覆盖的 OS/硬件/交互测试，单独执行并留存证据 |
| 执行证据检查 | 命令、日志、退出码、测试计数、运行 URL、Commit SHA 可追溯 |

### 6.1 CI 规则

1. CI 必须在固定目标 Commit 上实际触发，不能只在本地运行成功。
2. 必须提供：运行 URL、固定 Commit SHA、通过/失败/跳过数量、失败阶段。
3. 必需检查失败时，不得宣布 `READY_FOR_INDEPENDENT_AUDIT`。
4. 契约完整性检查必须是独立、始终执行的检查；不得因其他测试失败而被跳过。
5. 不得通过删除测试、放宽断言、静默跳过必需测试来制造绿色结果。
6. 因环境限制确实无法运行的测试，必须单独归类、显式标注跳过原因，并提供真实环境验证证据；不得把“跳过”当作“通过”。
7. 本地测试结果不得冒充 GitHub CI 结果。
8. 不得因 CI 工作流文件存在或曾经运行过，就认定 CI 已建立完成；必须在固定目标 Commit 上实际触发，并检查全部必需检查的结论。

### 6.2 环境差异

- 必须显式检查 Linux 与 macOS 的路径、命令、文件系统、Docker、权限和签名差异。
- 必须在 Linux CI 上确认没有误跑只在 macOS 可用的专项测试；反之亦然。
- macOS 专项测试（Keychain、LocalAuthentication、Secure Enclave、签名产物等）无法在 Linux CI 运行时，应单独归类并在真实 Mac 上验证。

## 7. G3｜独立验收

1. 只有满足 G0–G2，才能正式移交 Agent 2。
2. Agent 2 必须在固定 Commit 上独立检查：契约、Diff、测试、CI 结果、真实环境证据和缺陷记录。
3. Agent 3 **不得自行宣布最终 PASS**；开发方自述不能替代独立证据。
4. 如果 Agent 2 无法访问某项必要环境，应标记 `WAITING`，写明缺失环境和所需证据；不得用开发方叙述补足。
5. 验收发现的问题回到 G1/G2 修复，形成新的固定 Commit 后重新验证；不得在未重新验证的情况下沿用旧结论。
6. 最终 `PASS` / `FAIL` 由独立验收方或用户给出。

## 8. 证据与记录

每个工作包至少记录：

- 工作包编号、范围、明确不做的事项；
- 固定基线 Commit、分支、目标 Commit；
- 契约路径、字节数、SHA-256、AC/E2E/EV 数量；
- 开发环境与真实验证环境（OS、架构、运行时、依赖、签名身份、Docker 等）；
- 复现命令、修复前后结果、测试计数（通过/失败/跳过）；
- CI 运行 URL、必需检查结论；
- 缺陷记录与根因；
- 已知限制、未验证项、需要用户提供的条件；
- 用户亲自完成的操作（只记录“已完成/未完成”，不记录密码或生物识别数据）。

## 9. 禁止事项

本轮及后续同类工作不得：

- 修改正式冻结验收契约；
- 在未授权时开发下一轮业务功能（例如 FIX4）；
- 大规模重构 JARVIS；
- 修改 `main`；
- 禁用安全测试、删除测试或放宽断言以制造通过；
- 擅自降低身份认证标准；
- 将本地测试结果冒充 GitHub CI；
- 将模拟认证结果冒充真实 macOS 认证；
- 将开发完成冒充独立验收通过；
- 擅自购买订阅或引入未获用户批准的外部依赖。

## 10. 门禁结论矩阵

| 门禁 | 通过条件 | 未通过时的状态 |
|---|---|---|
| G0 开发准备 | 固定版本、契约、范围、输入、技术前置、环境全部核实 | `BLOCKED` |
| G1 技术与实现 | 高风险方案有最小实验；缺陷有旧失败/新通过证据 | `BLOCKED_FEASIBILITY` / 继续修复 |
| G2 自动质量 | 单元、注入、集成、CI、真实环境、证据全部满足 | 不得移交；`CI_BLOCKED` 等 |
| G3 独立验收 | Agent 2 在固定 Commit 上独立复核 | `WAITING` / `FAIL` |

只有 G0–G3 全部满足，才能给出整个工程任务的 `READY` / `PASS` 结论。
